# План разработки — редакция 2.0

Дата: 30.10.2026. План заменяет более тяжёлую редакцию 1.0. Разработка ведётся под 1–2 пользователей и отдельные Excel-книги организаций.

## 1. Согласовать примеры и поля — 1–2 рабочих дня

- Получить образец книги/бланков при наличии; иначе создать синтетический пример.
- Уточнить, один или два компьютера используются; базовое решение — последовательная работа с одной книгой.
- Зафиксировать листы и обязательные поля, статусы, формулы и правила периодичности.
- Согласовать общий код 000000, поля бумажного бланка и внесение номеров после регистрации.
- Проверить нормативный профиль и порядок позднего ввода с ответственным за ОТ. Ожидание согласования отдельно от времени разработки.

Результат: словарь колонок, пустой бланк обычного/ручного режима и пример заполненной книги.

## 2. Книги организаций и запуск — 2–3 дня

- Каркас Python, локальный сервер, страницы, ярлык и единственный экземпляр.
- Создание/подключение организаций, UUID книг, независимые пути и счётчики.
- Репозиторий Excel: чтение, валидация, резерв, временная запись и замена.
- Простая блокировка и обнаружение внешнего изменения, журнал действий.
- Первая Windows-сборка до разработки всех экранов.

Готово, когда две организации сохраняют независимые данные, книга не перезаписывается при конфликте, EXE работает без установленного Python.

## 3. Ввод, планы и сроки — 3–5 дней

- Работники, история переводов, инструктирующие/полномочия.
- Автодополнение и проверки, массовое планирование по выбранным работникам.
- Плановая и предельная даты, подсветки и фильтры; сводка организаций.
- Расчётные колонки и форматирование Excel; независимый расчёт интерфейса.
- Регистрация факта, уникальные номера, простой архив и следующий повторный.

Готово, когда основной путь работает без прямого редактирования ячеек, а предупреждения интерфейса не зависят от кэша формул Excel.

## 4. Печать и полностью ручная бумага — 2–4 дня

- Заполненные формы и пустые организационные формы с кодом 000000.
- DOCX, конвертация PDF при наличии LibreOffice.
- Форма ввода бумаги, связь с планом, поиск похожих документов, реальные даты.
- Обработка пачки накопленных повторных без лишних устаревших планов.
- Отображение выданного номера для оригинала, опись пакета.

Готово, когда можно заранее распечатать запас, провести бумажный процесс без компьютера, затем внести его один раз в правильную книгу.

## 5. Прямой Excel и резервирование — 2–3 дня

- Открытие Excel с резервом и блокировкой записи этой организации.
- Проверка/перечитывание и простой отчёт изменений по ID.
- Новые строки без ID, контроль дублей, ссылок и номеров.
- Дневные копии, ротация, экспорт комплекта, восстановление с проверкой счётчиков.
- Обнаружение изменений между запусками.

Готово, когда сортировка книги не ломает связи, корректные ручные изменения принимаются, ошибочные ячейки показываются пользователю, восстановление испытано на отдельной копии.

## 6. Проверка и поставка — 2–3 дня

- Сценарии ACCEPTANCE.md, чистая Windows, офлайн, Excel открыт, два окна браузера.
- Физическая печать и проверка места для ручного заполнения.
- Инструкция на несколько страниц и поставка папки EXE с ярлыком.
- Пилот на копии реальных данных и исправление критичных ошибок.

Готово, когда оператор самостоятельно выполняет обычный ввод, бумажный ввод, ручную правку Excel и восстановление по инструкции.

## Оценка

Ориентир: 12–20 рабочих дней одного разработчика после фиксации понятных примеров. Резерв 20–30% даёт примерно 15–26 дней. Это оценка упрощённого объёма, а не срок обязательства. Разбор повреждённой исторической книги, очистка данных и ожидание правового согласования оцениваются отдельно.

Первую демонстрацию нескольких организаций, формы ввода и подсветки сроков можно получить после этапов 1–3. До ежедневной эксплуатации необходимо завершить бумажный режим, ручной Excel, резервирование и проверку поставки.

## Как вести GitHub

Один небольшой репозиторий, 6 milestones по этапам. Код, шаблоны и синтетические примеры — в Git. Персональные данные, реальные книги, output, backups, logs и пользовательские настройки исключаются. README содержит запуск разработчика и сборку Windows.

Структура без излишнего дробления:

```text
src/ot_registry/
  launcher.py
  config.py
  excel_store.py
  organizations.py
  services.py
  validation.py
  deadlines.py
  printing.py
  web.py
  templates/
  static/
resources/forms/
tests/
docs/
pyproject.toml
```

Разделение сервисов на несколько модулей допустимо по мере роста. Сложный фреймворк предметных слоёв не является требованием. Веб-маршруты не пишут ячейки напрямую: сохранение всё равно централизовано в excel_store.

Приоритетные проверки: изоляция организаций; дата факта против даты ввода; повторная отправка; общий код 000000; связь бумаги с планом; расчёт месяцев; резерв и отказ записи при конфликте. Проверки выполняются на временных синтетических XLSX. Избыточное покрытие каждого элемента интерфейса тестами не нужно.
