# Правила работы с репозиторием

Документ обязателен для всех участников разработки (людей и автоматизированных агентов).

## 1. Ветки и коммиты

1. `main` — стабильная ветка. Прямая разработка в `main` не ведётся.
2. Работа идёт в тематической ветке: `feature/<краткое-название>`, `fix/<...>`, `docs/<...>`.
3. **Обязательно делать промежуточные коммиты в рабочую ветку** после каждого логически
   завершённого шага. Прогресс не должен зависеть от сохранности среды разработки: если среда
   потеряна, по последнему коммиту должно быть понятно, что сделано и что осталось.
4. Один коммит — одно осмысленное изменение. Не смешивать рефакторинг, новую функцию и
   правку документации без необходимости.
5. Формат сообщения: `<область>: <краткое описание>` (например,
   `excel_store: атомарная замена книги и резерв перед записью`).
   В теле коммита — что изменилось и почему, если причина не очевидна.
6. Не коммитить секреты, токены, пароли, реальные персональные данные и рабочие книги.
   Токены доступа передаются только через переменные окружения или менеджер секретов.
7. Перед коммитом: `python -m pytest -q` должен проходить (или в коммите явно указано,
   почему тесты не запускались).

## 2. Журнал работ (workbook)

1. Файл `docs/WORKBOOK.md` — обязательная часть проекта.
2. В него записывается **каждое** существенное изменение и решение:
   дата, что сделано, почему выбран такой вариант, какие альтернативы отклонены,
   что осталось незавершённым и какие есть риски.
3. Записи ведутся по ходу работы, а не восстанавливаются в конце. Перед каждым коммитом
   проверяется, что сделанное отражено в журнале.
4. Решения, меняющие модель данных, схему Excel или поведение пользователя, фиксируются
   отдельной записью с обоснованием.
5. Журнал не переписывается задним числом: ошибочное решение помечается как отменённое
   с датой и причиной.

## 3. Вопросы заказчику

1. Вопросы, без ответа на которые нельзя двигаться дальше, кладутся в `user_polls/`.
2. Имена файлов — последовательные: `0001_topic.txt`, `0002_topic.txt` и т. д.
   Внутри — нумерованные вопросы с местом для ответа.
3. Обработанные файлы переименовываются в `0001_topic_processed.txt`;
   в журнал работ вносится, какие ответы учтены.
4. О создании нового файла с вопросами сообщается в чате/задаче.

## 4. Данные и совместимость

1. Формат книги Excel меняется только через миграцию; существующие данные должны читаться.
2. Каждая запись идентифицируется постоянным UUID, а не номером строки или ФИО.
3. Даты в книге — даты Excel с форматом `ДД.ММ.ГГГГ`; в API и коде — ISO `YYYY-MM-DD`.
4. Запись в книгу выполняется только через `excel_store`; прямых правок ячеек из веб-слоя нет.
5. Формулы в книге — для отображения. Критичные значения сохраняются обычными ячейками.

## 5. Качество

1. Автотесты на доменную логику обязательны; интерфейс проверяется сценариями из
   `docs/ACCEPTANCE.md`.
2. Ошибки пользователю показываются понятным текстом на русском, без трассировок.
3. Нельзя сообщать об успешном сохранении, если запись не подтверждена.
4. Требования к поведению описываются в ТЗ; спорные случаи выносятся в `user_polls/`.
